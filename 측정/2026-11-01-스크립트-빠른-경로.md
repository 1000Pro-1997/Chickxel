# 스크립트 효과 빠른 경로 (2026-11-01)

`측정/2026-11-01-스크립트-효과-컴파일.md`의 시험판을 Core에 넣은 빠른 경로(`src/Chickxel.Core/Scripting/Fast/`)를 쟀다. 시험판과 달라진 점은 둘이다.

- 문장 수를 Jint 4.17과 같은 규칙으로 센다(설계 8장 1번 결정). 시험판은 반복 횟수를 셌다.
- 부분집합을 정하고 의미를 다듬었다: 블록 범위와 TDZ, 계산 순서, JS 숫자 규칙(Jint 구현을 그대로 옮김), 실행 중 Jint로 넘기는 자리.

잰 것: 속도(Jint, 빠른 경로, 기본 C# 렌더러), 컴파일 시간, 문장 계수기 비용(계수기를 넣은 코드와 뺀 코드), 무한 반복이 멈추는 시간, 숫자 계산만으로 Jint 메모리 한도에 닿는 경우.

## 환경

- Windows 11 x64, Intel Core i5-13400F(논리 코어 16개), 메모리 64GB
- .NET SDK 10.0.300, Release, Jint 4.17.0(커밋 `f0e4cbb5`), Acornima 1.7.0
- 측정 코드: 저장소 밖 임시 프로젝트(`%TEMP%\chickxel-fastbench`). Core의 internal을 부르려고 어셈블리 이름을 `Chickxel.Core.Tests`로 빌렸다. 계수기를 뺀 판은 `Scripting/Fast/*.cs`를 그 프로젝트에 복사해 `Charge`가 빈 식을 돌려주게 고쳐 만들었다(같은 복사본에서 계수기를 켠 판이 Core 판과 같은 시간이 나와 복사본이 같은 코드임을 확인). 저장소에는 넣지 않았다.

## 부분집합

빠른 경로는 render만 바꾼다. 선언 읽기와 `padding`은 늘 Jint다. 아래 밖의 것이 render에서 닿을 수 있는 자리에 있으면 그 원문의 render는 통째로 Jint로 돌고, `ScriptEffectProgram.ExecutionPath`가 처음 걸린 구문의 까닭과 줄·칸을 알려 준다.

| 넣은 것 | 뺀 것(Jint로) |
|---|---|
| 맨 위: `effect({ … })` 하나(선언 객체 안은 리터럴·배열·객체·함수만), `const`(숫자·참거짓 식, 함수, render에서 읽지 않는 리터럴 묶음), `function` 선언 | 맨 위의 다른 문장, `let`/`var`, 선언 객체 안의 함수 호출·getter·계산 키·펼침 |
| `let`/`const`(숫자·참거짓 변수, 그림·색·함수 별칭), `if`, `for`, `while`, `do … while`, 이름 없는 `break`/`continue`, `return`, 블록, 빈 문장 | `var`, `switch`, `try`, `throw`, 이름표, `for … in/of`, 클래스, 생성기, async, 구조 분해, 기본값·나머지 매개변수 |
| 숫자 연산, `**`, 비교, 비트 연산(ToInt32/ToUint32), 논리 연산(조건 자리에서는 종류가 섞여도 됨), 조건식, 쉼표, 증감, 복합 대입 | 문자열, 객체·배열 리터럴, `undefined`/`null`, 숫자와 참거짓이 섞인 값, `??`, 논리 대입, `typeof`, `delete`, 선택적 연결 |
| `Math` 상수와 abs, acos, asin, atan, atan2, ceil, clz32, cos, cosh, exp, floor, fround, hypot(인자 3개까지), imul, log, log10, log2, max, min, pow, round, sign, sin, sinh, sqrt, tan, tanh, trunc | fdlibm으로 계산하는 cbrt, expm1, log1p, acosh, asinh, atanh와 f16round, sumPrecise |
| `NaN`, `Infinity`, `lerp`, `hsvToRgb`, `rgbToHsv` | 그 밖의 전역(`Number`, `Object` …) |
| `img.width/height/data`, `d[i]` 읽기·쓰기, `d.length`, `s.키`(int·number·bool·color, choice는 문자열 리터럴과 `===`/`!==`/`==`/`!=`만), `ctx.t/progress/frame/step/span/source/pivot`, `ctx.color("키")`, `ctx.hash`, `ctx.random` | `img.blank`, `blendOver`, `ctx.frameSource`, choice 값을 그 밖에 쓰기 |
| `const`에 묶은 화살표·`function`과 `function` 선언(부르는 자리에 펼침, 인자 수가 매개변수보다 많으면 남는 인자도 계산) | 재귀, 함수를 돌려주기, 매개변수보다 적은 인자, 값을 돌려주지 않는 블록 몸통 함수의 결과 쓰기 |

- `Math.*`와 `%`, `**`, ToInt32는 Jint의 구현(`MathInstance`, `JintBinaryExpression`, `TypeConverter`)을 그대로 옮겨 비트까지 같은 값을 낸다. 규격이 아니라 Jint가 기준이다. 예: `Math.round`는 짝수 쪽 반올림 뒤 정확히 .5였으면 위로, `Math.LOG2E`는 `Math.Log(Math.E, 2)`.
- `hsvToRgb`, `rgbToHsv`, `ctx.hash`, `ctx.random`은 `ScriptHostApi`와 같은 함수(`Color32.FromHsv`, `Color32.ToHsv`, `LayerEffects.Random`)를 같은 형 변환으로 부른다.
- 실행 중 결과가 갈릴 수 있는 자리에서는 그 호출만 그림을 건드리지 않고 Jint로 다시 그린다: 배열 밖·정수 아닌 칸 읽기·쓰기, 값으로 쓰는 함수가 값 없이 끝남(`return;` 포함), 식 몸통 화살표 함수에서 문장 한도에 걸림(아래).
- 메모리: 빠른 경로는 호출마다 작은 배열 몇 개(ctx, 설정)와 data 배열만 쓴다. data 배열은 스레드마다 다시 쓰되 512² 그림(8MB)까지만 잡아 두고, 더 큰 그림은 호출마다 만든다.

## 문장 수 규칙을 Jint와 맞춘 방법

Jint 4.17 원문(NuGet 패키지에 적힌 커밋 `f0e4cbb5`)을 읽고 계수 자리를 그대로 옮겼다.

- 앱의 실행기에는 정확히 세야 하는 제약이 셋이다(문장 수, 메모리, 호출마다 바꾸는 취소 제약). 그래서 Jint는 계수기만 따로 세는 빠른 길을 끄고 일반 길(`RunPerStatementChecks`)로 센다.
- 문장 수는 바깥 호출에 들어갈 때마다 0으로 돌아간다(`ExecuteWithConstraints`). render는 `Invoke` 한 번이므로 맨 위(선언) 실행의 문장은 render 한도에 들어가지 않는다.
- Jint가 1을 세는 자리와 빠른 경로가 1을 세는 자리:

| Jint 원문 | 세는 것 |
|---|---|
| `JintStatement.Execute` | 블록이 아닌 문장 하나를 실행할 때마다(`if`, `for`, `while`, `do`, 선언, 식 문장, `return`, `break`, `continue`, 빈 문장, 지시문 `'use strict'`, 함수 선언 문장도) |
| `JintStatementList.Execute` | 문장 목록을 실행할 때마다 1: 함수 몸통(문장이 하나여도), 문장이 하나가 아닌 블록(빈 블록 포함) |
| `JintBlockStatement` 한 문장 길 | 문장이 하나뿐인 블록은 블록을 세지 않고 그 문장만 |
| `JintStatementList` + `FastResolve` | 문장 목록 바로 안의 리터럴 `return`(`return 0;`)은 실행하지 않고 값만 꺼내 세지 않는다. `if (x) return 0;`의 `return`은 센다 |
| `JintFunctionDefinition.EvaluateBody` | 식 몸통 화살표 함수를 부를 때마다 1(`lerp`도 JS 화살표 함수라 1) |
| `JintForStatement` | `for`의 `let`/`const` 초기화는 문장으로 실행되어 1. 조건·증감식은 세지 않음 |

- 한도는 `++count > MaxStatements`이면 그 문장 앞에서 멈춘다. 빠른 경로는 지역 계수기를 문장마다 1 줄이고, 다 쓰면 다음 몫(4096)을 받는다. 몫의 합이 정확히 `MaxStatements`라 같은 문장에서 멈춘다. 몫을 받을 때 취소와 시간도 본다.
- 멈춘 위치: Jint는 한도 오류의 줄·칸을 호출 스택 첫 줄(마지막 구문 요소의 끝 줄, 시작 칸 + 1)에서 읽는다. 문장과 문장 목록에서는 그 요소가 세는 문장·블록이라 빠른 경로가 계수 자리마다 같은 위치를 적어 둔다. 식 몸통 화살표 함수는 Jint가 위치를 바꾸지 않고 세서 미리 알 수 없으므로, 그 자리에서 한도에 걸리면 그 호출을 Jint로 다시 돌려 Jint의 오류를 그대로 낸다.

근거가 되는 시험(`tests/Chickxel.Core.Tests/ScriptFastPathTests.cs`): 빠른 경로가 센 문장 수 N마다 한도 N + 1, N이면 두 길 모두 끝까지 그리고 N − 1이면 두 길 모두 같은 종류·줄·칸에서 멈춘다(Jint는 실행기의 계수 제약 한도를 그 호출 동안만 바꿔 같은 실행기로 돌림). 구문 묶음 9개와 본보기는 한도 1~150 전부와 무작위 40개에서도 멈추는 자리가 같았다. 가장자리 값 식 63개는 N − 1, N, N + 1을 봤다. 무한 반복 5종(식 몸통·블록 몸통 함수를 부르는 반복 포함)은 공개 `Render`의 오류(종류·줄·칸·문구)가 Jint와 같다.

## 무한 반복

`let x = 0; while (true) { x++; }`(기본 한도 5천만 문장): 빠른 경로 8~10ms, Jint 1.3~2.0초. 둘 다 문장 한도(같은 줄·칸)로 멈춘다.

## 결론

- 본보기와 시험 원문 묶음에서 빠른 경로가 Jint와 배열 값(double 비트)까지 같고, 본보기는 기본 렌더러와 픽셀까지 같다.
- 문장 수를 Jint와 같은 자리에서 세어, 한도 바로 아래·꼭 맞음·바로 위에서 두 길이 같은 문장에서 멈추고 같은 오류(종류·줄·칸·문구)를 낸다.
- 계수기를 넣은 빠른 경로는 Jint보다 41~115배 빠르다. 계수기 비용은 빛 지나가기에서 계수기를 뺀 render 시간의 14~56%다.

## 남은 문제

- Jint의 메모리 한도는 호출 동안 할당한 바이트를 센다(256MB). Jint는 소수 결과마다 숫자 객체를 만들어, 숫자 계산만 하는 원문도 이 한도에 닿는다. 빠른 경로는 할당하지 않으므로 이런 원문은 빠른 경로에서 그려지고 Jint(이 변환기 이전 앱, 부분집합 밖, Jint로 넘긴 호출)에서는 메모리 오류로 그려지지 않는다. 결정: 메모리 한도는 시간 한도처럼 폭주를 막는 안전망으로 보고, 결과를 정하는 규칙은 문장 수다. 잰 값(render 안 `let a = 0.5; for (let i = 0; i < 24000000; i++) <식> img.data[0] = a % 256;`):

| 식 | Jint 할당(100만 번당) | Jint | 빠른 경로 |
|---|---|---|---|
| `a = a * 1.0000001 + 0.1;` | 64MB | 메모리 한도(354ms, 할당량으로 계산하면 약 400만 번째) | 끝까지(42ms) |
| `a = (a + i) % 1000;` | 64MB | 메모리 한도(413ms) | 끝까지(253ms) |
| `a += i & 7;` | 0MB(정수) | 끝까지(1,148ms) | 끝까지(31ms) |

- 시간 한도는 두 길 모두 기계마다 멈추는 자리가 다르다(빠른 경로는 4096문장마다 본다). 느린 기계의 Jint는 문장 한도 전에 시간 한도에 닿을 수 있다.
- Jint 판을 올리면 계수 자리(`JintStatement`, `JintStatementList`, `JintBlockStatement`, `JintFunctionDefinition`)와 `Math` 구현을 다시 확인해야 한다. 비교 시험(`ScriptFastPathTests`)이 차이를 잡는다.
- 줄 단위 병렬, 반복 변수·`x | 0`의 int 판정은 아직 하지 않았다(시험판 문서의 다음 후보 그대로).

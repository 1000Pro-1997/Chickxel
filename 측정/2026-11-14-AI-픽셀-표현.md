# AI가 픽셀을 읽고 그리는 방식 비교 (2026-11-14)

## 무엇을 왜 쟀나

AI 채팅·외부 AI 연결에서 결과가 가장 잘 나오는 구성을 찾으려고, 실제 Claude Code·Codex CLI에 두 가지를 시켜 비교했다.

1. **캔버스를 어떤 글 형식으로 줄 때 가장 정확히 읽고 고치나**(`get_pixels`·`get_reference`·`get_folder_image`가 돌려주는 형식). "색 배열(JSON)로 주는 게 AI에게 편하지 않냐"는 질문에 답하려는 것.
2. **어떤 지시(그리기 요령)·진행 방식에서 그림이 가장 잘 나오나**: 요령 없음 / 요령 모두 / 고친 요령 / 정지 그림 요령만 끔 / 한 차례 안에서 후보 두 장을 그려 고르기.

## 환경

- Windows 11 (10.0.26200), x64. Python 3.12, Pillow 12.3.
- Claude Code 2.1.325, 기본 모델(사용자 설정 — 목록 이름 "Opus 4.8"). Codex CLI 0.169.0, 기본 모델(`config.toml` — GPT-5.6-Sol).
- 각 CLI는 앱과 같은 식으로 띄웠다: Claude는 `-p --system-prompt-file`, Codex는 `exec`(+`resume`)에 `developer_instructions`. 측정 코드는 저장소에 넣지 않았다(임시 폴더 `%TEMP%\pxbench`의 `pxlib.py`·`bench.py`·`canvas.py`·`draw.py`·`judge.py`).

## 1. 읽기·고치기 정확도

### 방법

- 그림: 내장 예시 `hero`(32×32, 14색), 가이드 예시 `wolf.png`(49×98, 33색), `hero`를 2배로 키운 64×64(같은 글자가 길게 이어지는 경우).
- 형식 6가지(같은 그림을 각각으로 바꿔 줌):
  - `grid`: 지금까지의 범례 + 한 줄에 한 글자씩
  - `grid_ruler`: `grid` + x 눈금 줄(십·일의 자리) + 줄마다 `y|`
  - `grid_spaced`: 글자 사이 빈칸 + `y=N:` + x 머리줄
  - `json_hex`: `pixels[y][x] = "#RRGGBB"|null` 2차원 배열
  - `json_index`: 팔레트 + 번호 2차원 배열
  - `runs`: 줄마다 `x0-x1 글자` 구간
- 과제(정답과 자동 비교): 좌표 12곳 색 읽기(`lookup`, 64×64 `lookup2x`), 한 색의 경계 상자(`bbox`, IoU), 한 색 개수(`count`), 고친 그림 전체를 같은 형식으로 돌려받기 — 2px 옮기기(`shift`)·좌우 뒤집기(`mirror`)·위 절반만 색 바꾸기(`recolor`)·64×64에 6점 찍기(`mark`, 맞은 픽셀 비율).
- 모델 2 × 형식 6 × 과제 11 × 2번 = 264회. 도구 없이 글로만 답하게 했다.

### 결과 (점수 1 = 모두 맞음, 형식마다 과제 평균)

| 형식 | Claude | Codex | 64×64 색 읽기 (Claude / Codex) |
|---|---|---|---|
| grid (예전) | 0.975 | 0.975 | 1.00 / 0.96 |
| **grid_ruler** | **0.989** | **0.991** | 0.96 / 1.00 |
| grid_spaced | 0.989 | 0.928 | 0.96 / 0.67 |
| json_hex | 0.854 | 0.855 | 0.67 / 0.33 |
| json_index | 0.889 | 0.931 | 0.42 / 0.71 |
| runs | 0.989 | 0.972 | 1.00 / 1.00 |

- 색 배열(JSON)은 두 모델 모두 가장 나빴다. 특히 큰 그림에서 좌표를 짚는 일(64×64 색 읽기 0.33~0.71)과 Claude의 그림 전체 다시 쓰기(옮기기 0.81, 뒤집기 0.74)에서 틀렸다. 글자 수도 `grid`의 약 7배다.
- 눈금을 붙인 격자(`grid_ruler`)가 두 모델에서 함께 가장 높았다. 빈칸 격자는 Claude는 좋지만 Codex는 나빴고, 구간(`runs`)은 경계 상자에서 Codex가 0.80으로 흔들렸다.

## 2. 그리기 결과

### 방법

- 화면 대신 같은 도구를 흉내 낸 `canvas.py`(draw_pixels·set_pixels·도형·채우기·지우기·색 바꾸기·프레임·`image`(키운 PNG를 모델이 직접 봄)·`pixels`·참고 예시·그림 규칙)를 쓰게 하고, 앱처럼 두 차례로 돌렸다: 요청(+직접 찍기 줄) → 앱의 자동 검토 지시.
- 요청(대충 말한 한국어): 기사 캐릭터(32×32), 체력 포션 아이콘(16×16), 숲 나무(32×32), 통통 튀는 슬라임 4프레임(16×16), 흐린 그림 도트답게 다듬기(32×32, 47색), 두 프레임 사이 중간 프레임 넣기(32×32).
- 구성:
  - `base`: 기본 규칙만(요령 없음)
  - `tips`: v1.14.129의 그리기 요령 모두
  - `tips2`: 요령 고침(비율·자세·덩어리 잎·점프 늘이고 누르기), 다듬기·보강은 눈금 격자로
  - `tipsdef`: 정지 그림 요령(기본 그리기 순서·사람·물체·배경)을 끄고 나머지만
  - `cand2`: 한 차례 안에서 후보 두 장을 그려 하나만 남기기
- 모델마다 구성마다 2번. 결과 그림을 과제마다 한 장에 섞어(이름 가림) Claude와 Codex가 각각 1~10점(요청에 맞음·픽셀 아트 솜씨·전체)으로 매기고, 두 채점의 평균을 썼다.
- 한 번 그리는 데 걸린 시간(두 차례 합): 중앙값 Claude 117~173초, Codex 101~159초(구성마다), 가장 긴 것 475초.

### 그 밖에 본 것

- **같은 부탁도 그릴 때마다 차이가 크다.** 같은 구성 두 번 중 나은 쪽만 고르면(채점 기준) 평균이 6.71~6.92 → 7.08~7.75로 0.5~0.8점 올랐다. 지시문을 바꾼 어떤 차이보다 크다.
- 두 채점이 둘 중 나은 쪽을 같게 고른 것은 17번, 다르게 고른 것 7번, 같은 점수 12번이다. 한 모델의 선택만 따라도 평균 7.24~7.32로 대부분 따라간다.
- 그런데 **한 차례 안에서 두 장을 그려 고르게 하면(cand2) 오히려 낮았다**(6.58). 두 번째 후보가 첫 후보만 못하거나 시간이 나뉘는 것으로 보인다. 나은 쪽을 고르는 이득은 따로 처음부터 다시 그린 결과를 사람이 고를 때만 확인됐다.
- 자동 검토 차례가 바꾼 픽셀은 0~9%(대부분 5% 아래)였다. 결과는 거의 첫 그림에서 정해진다.
- 중간 프레임 과제는 거의 모두 정답(위로 2px) 그대로였고, 요령의 "느린 쪽에 가깝게" 문구 때문에 2번은 1px·3px로 넣었다(0.78).
- 사용량: 측정 중 Claude는 5시간 한도, Codex는 사용량 한도에 한 번씩 걸렸다. 한도에 걸린 실행은 지우고 다시 돌렸다.

## 결론과 반영

- **`get_pixels` 등 픽셀 글에 x 눈금과 `y|`를 붙였다.** 색 배열(JSON)은 쓰지 않는다. `draw_pixels`는 `y|`가 붙은 줄을 그대로 받아도 머리를 떼고 그린다.
- **그리기 요령의 처음 값을 바꿨다.** 정지 그림용 요령(기본 그리기 순서·사람·물체·배경)은 평균을 높이지 못했고 기사에서는 낮췄으므로 처음엔 끈다. 움직이는 동작 요령은 애니메이션 점수를 올렸으므로(5.5 → 6.5~7.4) 움직임·프레임 보강·다듬기·폴더 참고는 켠다. v1.14.129 설정에도 한 번 옮긴다(사용자가 고칠 수 있음).
- **한 차례 안에서 후보 여러 장을 그리는 기능은 넣지 않았다**(측정에서 낮아짐).

## 남은 문제

- 칸마다 2번씩이라 0.3~0.5점 차이는 오차 안이다. 기사(base가 뚜렷이 높음)와 슬라임(요령이 뚜렷이 높음)만 믿을 만하다.
- 채점은 AI 두 개가 했다. 서로 남의 그림을 더 높게 주는 경향은 없었지만(Claude 채점 Claude 6.28·Codex 5.61, Codex 채점 Claude 7.31·Codex 7.64) 사람 눈과 다를 수 있다.
- 다시 채점하면 같은 그림의 점수가 0.5점 안팎 바뀌었다.
- 그림 생성 방식(Codex 이미지 생성 → 변환)은 재지 않았다.
- 두 장 중 고르는 이득을 앱에서 얻으려면 처음부터 따로 다시 그린 결과를 사람이 고르게 해야 한다(지금은 마지막 메시지를 고쳐 다시 보내는 것으로 가능).

# 스크립트 효과 컴파일 시험 (2026-11-01)

스크립트 효과 JS를 Jint로 해석해 돌리는 대신, 앱이 읽을 때 .NET 식 트리(`System.Linq.Expressions`)로 바꿔 컴파일하면 얼마나 빨라지는지, 결과가 Jint와 바이트까지 같은지 재 봤다. 시험한 원문은 `src/Chickxel.Core/Scripting/Templates/shine.js`(빛 지나가기) 하나다.

## 환경

- Windows 11 x64, Intel Core i5-13400F(논리 코어 16개), 메모리 64GB
- .NET SDK 10.0.300, Release, Jint 4.17.0, Acornima 1.7.0(Jint 내장 파서)
- 측정 코드: 저장소 밖 임시 프로젝트(`%TEMP%\chickxel-jsjit`). Core의 internal(`ShineRender`, `ScriptHostApi.ToByte`, `LayerEffects.PivotIn`)을 부르려고 어셈블리 이름을 `Chickxel.Core.Tests`로 빌렸다. 저장소에는 넣지 않았다.

## 시험판 구조

- 파싱: Acornima로 원문을 읽는다. 맨 위는 `effect({ … render … })` 하나와 const 숫자·함수, function 선언만 받는다.
- 허용한 부분집합만 식 트리로 바꾼다: let/const 숫자·참거짓 변수, if·for·while·do, break·continue, 숫자 연산·비교·비트 연산(JS ToInt32 규칙), `Math.*`(round·sign·pow는 JS 규칙 도우미), `lerp`, `img.width/height/data`, `d[i]` 읽기·쓰기, `s.키`(int·number·bool·color), `ctx.t/progress/frame/step/span/source/pivot`, `ctx.color("키")`.
- const로 묶은 화살표 함수와 function은 부르는 자리에 펼친다(재귀는 거부).
- 그 밖(문자열, 객체·배열 만들기, `hsvToRgb`, `img.blank`, `blendOver`, `ctx.hash/random/frameSource`, choice 설정 등)을 쓰면 컴파일을 거부하고 그 원문은 통째로 Jint로 돈다.
- 숫자는 모두 `double`. `img.data`는 길이가 정확히 너비 × 높이 × 4인 `double[]`(같은 길이면 스레드마다 다시 씀). 끝나면 `Uint8ClampedArray` 규칙(`ScriptHostApi.ToByte`, 0~255 정수는 빠른 길)으로 그림에 되쓴다.
- 배열 칸 접근마다 "정수이고 0 ≤ i < 길이"를 검사하고, 아니면(JS에서는 `undefined`가 되거나 배열이 늘어나는 자리) 그 호출만 Jint로 다시 그린다. render는 같은 입력이면 같은 결과라 다시 그려도 된다.
- 반복마다 지역 카운터를 줄이고 4096번마다 시간·취소·총 반복 한도를 검사한다.

## 결과가 같은지

| 그림 | 경우 수 |
|---|---|
| 16×16, 48×32, 가장자리에 붙은 40×40, 빈 8×8 | 각 1,500 |
| 128×128, 256×256 | 각 120 |

각도·폭·세기·부드러움·진행(0~1, 11단계)·색을 무작위로 골랐다. 그림은 울퉁불퉁한 덩어리에 구멍과 반투명 픽셀을 섞었다.

- 6,240가지 모두 컴파일본 = Jint, 컴파일본 = 기본 빛 지나가기(`ShineRender.Apply`). 다른 경우 0건, Jint로 다시 그린 경우 0건.

| 벗어나는 경우 | 결과 |
|---|---|
| 배열 끝 너머에 쓰기 | Jint로 다시 그림 → Jint와 같은 오류 문구 |
| 배열 끝 너머 읽기(`undefined === 0`) | Jint로 다시 그림 → 같은 그림 |
| NaN·소수·범위 밖 값 쓰기 | 다시 그리지 않고 같은 그림 |
| 문자열 사용 | 컴파일 거부 → Jint만 |
| 무한 반복 | 컴파일본은 반복 한도(5천만 번)로 7ms에 멈춤, Jint는 문장 한도로 1.7초에 멈춤 |

## 속도

프레임 하나, 각도 45 · 폭 3 · 세기 80 · 부드러움 1 · 진행 0.5. 예열 3번 뒤 중앙값(Jint 15~40번, 나머지 300번).

| 크기 | Jint | 컴파일본 전체 | 컴파일본 render만 | C# 1스레드 | C# 자동 병렬 | Jint ÷ 컴파일본 | 컴파일본 ÷ C# 1스레드 |
|---|---|---|---|---|---|---|---|
| 64² | 3.663ms | 0.043ms | 0.016ms | 0.006ms | 0.008ms | 85배 | 7.1배 |
| 128² | 11.615ms | 0.168ms | 0.061ms | 0.020ms | 0.040ms | 69배 | 8.4배 |
| 256² | 42.758ms | 0.662ms | 0.313ms | 0.079ms | 0.037ms | 65배 | 8.3배 |

- Jint 값은 실행마다 흔들렸다(256²에서 35~43ms). 앞선 실행들의 Jint ÷ 컴파일본은 40~58배였다.
- 부록 B와 같은 양(128² 30프레임 전체, 세 번 중 가장 빠른 값): Jint 247~302ms, 컴파일본 5.0~6.8ms, C# 1스레드 0.7ms.
- "전체"는 그림 → `double[]` 변환과 되쓰기를 포함한다. 256²에서 약 0.35ms다.
  - 배열을 매번 만들 때 0.878ms → 되쓰기 빠른 길 0.785ms → 같은 길이 배열 다시 쓰기 0.662ms.
- render만 놓고 C#보다 약 4배 느린 까닭(추정): 모든 계산이 `double`, 배열 칸마다 double → int 변환과 정수·범위 검사, 1스레드.

## 컴파일 시간

| 항목 | 시간 |
|---|---|
| 첫 컴파일(컴파일러 자체 JIT 포함) | 30~35ms |
| 그 뒤 컴파일(중앙값) | 2.5~2.7ms |
| 참고: Jint `ScriptEffectProgram.Parse`(예열 뒤 중앙값) | 0.6~0.7ms |
| 참고: Jint 첫 실행(계획 문서 부록 B) | 683ms |

프로젝트를 열 때 작업 스레드에서 컴파일하고, 끝나기 전에는 Jint로 그리면 된다.

## 결론과 남은 문제

- 결과가 Jint와 같고 Jint보다 40~85배 빠르다. 정식 설계로 갈 만하다.
- 실행 한도 규칙이 두 경로에서 다르다(Jint = 문장 수, 컴파일본 = 반복 횟수). Jint가 한도로 멈추는 원문을 컴파일본은 끝까지 그릴 수 있어, 경로에 따라 결과가 갈린다. 두 경로가 같은 규칙으로 세거나 한쪽만 판정하게 정해야 한다.
- 검증한 원문이 하나다. 부분집합 범위를 정하고 여러 원문에서 두 경로를 바이트 비교하는 시험이 필요하다.
- 컴파일본은 공유 상태가 없어 줄 단위 병렬이 가능해 보인다(재지 않음).
- 재지 않은 다음 후보: 반복 변수·인덱스를 int로 자동 판정하고 `x | 0`(JS 뜻 자체가 32비트 정수)을 int로 처리하기. 배열 칸 검사 비용을 줄일 것으로 본다.
